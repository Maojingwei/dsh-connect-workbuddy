# 【存档】这类 400（渠道校验 / 11128）：先重试

> **本楼已从置顶撤下（2026-10-28，5.13.0 发布）。** 它讲的「手动再发一次」已经可以由插件自己做：
> 开关 `channelRejectContinue.enabled` 打开后自动发「继续」，但 5.13.1 起默认只发 **1** 次，且它
> 只是**最后兜底**，不是 11128 的修复。见 [#162](https://github.com/dingminhua/dsh-connect-workbuddy/issues/162)。
>
> **2026-10-29 的重要更正（#163）**：固定 system 指纹（identity / Web GUI / @ 路径 800 字整段）每一轮
> 逐字节相同，新回合不会把它换掉；同一份 body 打上百次都是 400，只改三处短语才 200。所以「手动/自动
> 再发一次」对这一族**无效**。5.13.1 起由 `prepareChatBody` 的按句改词处理；改词后仍 11128，多半是
> 新的固定指纹，重发同样无效。本楼 §2 ③(a) 的「轮次变了 body 也变了」只适用于**随轮次变化**的窄情况，
> 不能解释固定 system 段。下文保留为机制取证与报告模板；**先升级/改词，不要先重发**。
>
> 分类总表、实测事实、报告模板在 [#125](https://github.com/dingminhua/dsh-connect-workbuddy/issues/125)。
> 新证据请按 §4 的模板发到 [#162](https://github.com/dingminhua/dsh-connect-workbuddy/issues/162) 或 [#125](https://github.com/dingminhua/dsh-connect-workbuddy/issues/125) §3。

## 0. 一句话

| | |
|---|---|
| **是哪一类** | `http 400` + `code 11128` + `"type":"channel_reject"`，文案里点名「渠道校验」 |
| **先做什么** | **先升级到含按句改词的 5.13.1**（固定 system 指纹重发无效）；只有在改词层没命中、且怀疑内容随轮次变化时，才考虑手动再发一次 |
| **宿主会替你重试吗** | **不会**。这类 400 不在 DSH 的原地重试集里——`KIND_HOST_CODE` 只把 `soft_rate` 译成宿主认得的码，其余保持 `type` 原样（`src/shim.ts:379`、`:373` 的注释说明了这条规则：渠道门的判决对给定的提示词是**确定**的，原地重投同一份字节只会白烧预算）。所以「重试」这个动作必须由你按下发送 |
| **别在这些上面花时间** | 换账号、换区域、重装 WorkBuddy 官方客户端、改 UA、清缓存重登。门读的是**这**一份请求的内容，与账号/积分/额度/网络都无关（[#125](https://github.com/dingminhua/dsh-connect-workbuddy/issues/125) §4 有实测记录，[#87–#98](https://github.com/dingminhua/dsh-connect-workbuddy/issues/98) 的报告者就是在这上面花了时间） |

## 1. 你贴的那条 400 长什么样

逐字取自 [#160](https://github.com/dingminhua/dsh-connect-workbuddy/issues/160)：

```text
400: {"message":"workbuddy 上游失败：被网关的渠道校验拦截（不是账号、额度或网络问题）（http 400）
（code 11128，requestId be65951a-…）。命中的 system 提示开头：「You are a helpful assistant.」……
","type":"channel_reject","code":"channel_reject"}
```

两个判据，都不看上游那句 `displayTips`：

- **分类看业务码**，不看措辞。`11128` 这一族里有三道门（提示开头命中 / 缺会话 id 三件套 / 首条不是 system）共用同一个码，而上游对三道门给的 `displayTips` **一字不差**——那句话从来不是判据（`src/upstream.ts:752` 的 `statesBusinessCode`，5.12.3 起统一读信封业务码）。
- **不换号**。`channel_reject` 是三个不换号类别之一（`src/shim.ts:1585` 的 `isFailoverWorthy`）：闸读的是每条账号都会发的同一份请求，换号只是晚一轮拿回同一个拒绝，还多烧一次真实额度。

## 2. 「再发一次」到底在做什么

> **先说一个必须先讲清的分歧。** 代码注释里写的判据是「渠道门对给定的提示词是**确定**的」（`src/shim.ts:373`）——按这句话，同一份请求重发一万次也该是同一个 400。但现场反馈是「重试就能继续」。**这两句不能同时字面成立**，我没做过能判定谁对的对照实验，所以下面把「能确证的」与「只是候选解释的」分开写，不混着说。

**① 能确证：一条请求内部已经救过三轮，你还能看到报错 = 三轮都失败了。**
被拒后，插件在**同一个账号**上依次换三种形状重发：强制中性头 → 稀疏零宽扰动 → 密集零宽扰动（`src/shim.ts:1732` 起），三级全失败才把 400 交回给你。文案里的「，并已用强制中性头与…重试过」就是这三级的点名（`src/shim.ts:2071`）。

> **这是一条可以自查的判据**：若你的报错里**没有**「并已用…重试过」这半句，那这一轮**一级都没跑**——见 §3 的上半张表（≤4.14.1 阶梯不存在）或机制三（≤5.12.2 判族漏判）。这两种情况**先升级**，继续重试没有意义。

**② 能确证：救成功一次之后，同进程的后续请求直接走那个形状。**
任何一级成功，本进程就记住它，后续请求从该形状起步，不再每次先浪费一次注定被拒的请求（`src/shim.ts:1682` 的 `startPerturbed`、`:1749` 的 `channelNeedsPerturbation = true`）。这份记忆是**进程内**的（`src/shim.ts:1455`），重启插件或 DSH 会清掉。**所以卡住时不要靠重启解决**——重启只让你多付一次注定被拒的请求。

**③ 候选解释（未实测）：为什么隔一轮再发就能过。**
如果「重发有效」成立，那必定是因为**第二次送出去的不是同一份请求**。两个候选：

- **(a) 轮次变了，body 也变了。** 手动重发是一条新的 turn：宿主会重新追加 `Time sampled while preparing turn N, step M:`、`Current runtime context.` 这类随轮次变化的内容（`src/upstream.ts:2663` 的前缀清单就是为识别它们而写的），历史也多一轮。若被拒的指纹恰好落在这些随轮次变化的段上，第二次就不再命中。
- **(b) 网关侧并非严格确定**（边缘节点、带缓存的判定，或扫描超时后放行）。这一条**我没有任何证据**，只是不能排除。

> 换句话说：本楼的主张是**「把这条消息再发一次，多数情况下能继续」这个操作建议**，而不是「网关是随机拦的」这个机制断言。后者我没有证据，也不打算编一个。

**④ 版本条件：≤5.12.2 上，「重试」一次都不会被救。**
5.12.2 及更早，`11128` 的判族是 `body.includes('"code":11128')`——上游 JSON 多一个空格、或把码写成字符串，就漏判成 `client`。而三级救援的门是 `kind === 'channel_reject'`，于是**整套救援一次都不会跑**，你收到的却是「请按上面的提示调整后重试」。[#155](https://github.com/dingminhua/dsh-connect-workbuddy/issues/155) 那条消息就是这个形状：正文写着 `code 11128`，同一句却带着 `"type":"client"`。5.12.3 起改为读信封里的业务码。**在这一档版本上，「重试」会一直失败到升级为止**——这也是为什么本楼把「先看文案定版本」放在重试之前。

## 3. 先定版本，再谈重试

不用翻设置——**报错文案本身就是版本戳**（各版本 `src/shim.ts` 逐 tag 比对得出）：

| 你看到的文案 | 版本区间 | 意味着 |
|---|---|---|
| 「**命中的** system 提示开头：…」＋「插件已对已知的第三方 agent 指纹做归一化」，**没有**「并已用…重试过」 | **4.13.2 – 4.14.1** | 三级救援**还不存在**。而且回显取自插件自己润色后的 body，所以第一行永远是插件补的 `You are a helpful assistant.`——那句话单独发是 200，报出来只是误导。[#160](https://github.com/dingminhua/dsh-connect-workbuddy/issues/160) 贴的就是这一档 |
| 「**请求里被网关扫描的**消息开头：…」＋「，并已用强制中性头与…重试过」 | **4.15.1 – 5.12.2** | 阶梯在，但判族用的还是字节匹配——上游 JSON 多一个空格，整套救援就不跑（§2 ④） |
| 同上一行，且 `code 11128` 与 `"type":"channel_reject"` **互相一致** | **≥ 5.12.3** | 判族与展示读同一个值，救援才会真的跑 |

另有一条**与文案无关**的版本戳：

- **每次都要等到分钟级才回错** → **≤ 5.12.3** 的密集救援 rung 是 O(n²)：92 KB 要 82.7 s，130 KB 的提示词要两分多钟。从外面看，「跑了 82 秒」和「根本没跑」是同一件事——这也是 [#159](https://github.com/dingminhua/dsh-connect-workbuddy/issues/159) 「三级救援一级都没跑」这个观察的一个可解释来源。5.12.4 已改为线性扫描，同样是 92 KB，**82.7 s → 10 ms**，规则与输出逐字节不变。

> 升级路径：npm `latest` 为 **5.13.1**（2026-10-29）。插件市场点更新即可，不用重新登录 App。
> **≤4.14.1 的用户请先升级再看本楼**：那一档缺的不只是救援，还包括 5.12.3 的判族修复与 4.15.1 起的「回显宿主原始 body」。
> **5.13.1 起**已知的固定指纹在发出前按句改写，「先重试」对这一族不再是首选做法——见 [#162](https://github.com/dingminhua/dsh-connect-workbuddy/issues/162) 置顶。

## 4. 重试几次仍不行

按 [#125](https://github.com/dingminhua/dsh-connect-workbuddy/issues/125) §3 的模板贴证据。缺 `code` + `requestId` 的报告无法定位。另外两种情况请顺手带上：

- **每一轮都 400**，且证据行里被扫描的消息开头全部标着「不在插件已知名单里」→ 网关新增了词条。请把那条开头贴回来（[#159](https://github.com/dingminhua/dsh-connect-workbuddy/issues/159) 现场那条 `system` 有 130,345 字符；该事件里的 Web-GUI 提示段已由 5.12.3 的定向破坏覆盖）。
- **只有某一个模型失败** → 大概率不是这一类，先看码：`14003`（模型繁忙）是**模型级**限流，不换号、但**宿主会自动重试几次**（它有界，500 ms→10 s 退避），出口是换模型；`6020/6021/6022`（排队）既不换号、也**不会**被自动重发（插件明确告诉宿主不要重试），要等或换模型。分类见 [#125](https://github.com/dingminhua/dsh-connect-workbuddy/issues/125) §1。

**一句话收尾**：这一类 400 不是账号问题、不是额度问题、也不是网络问题——它是网关在读你这份请求的**内容**。**5.13.1 起**，已知的固定指纹在发出前就按句改写成同义写法，这是主修复；三级救援仍然会在请求内部兜一遍，自动「继续」只是默认关闭、默认 1 次的最后兜底。所以**先升级到 5.13.1 并重载插件**，不要先重发；如果文案里根本没有「并已用…重试过」那半句，那不是重试的问题，是版本问题（§3）。反复不过就按 §4 贴证据。
